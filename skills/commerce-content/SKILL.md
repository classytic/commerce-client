---
name: commerce-content
description: Integrate Brihot structured CMS pages with @classytic/commerce-client/content, including server rendering, cache revalidation, content identity and merchant editing. Use when wiring a storefront to Brihot Content.
---

Read [the content contract](../../content.md) before implementing. Check the
installed SDK version and the host framework's cache APIs; do not invent endpoints.

Use the separate `@classytic/commerce-client/content` import. Public reads need
`apiUrl` and the store slug, with no merchant token or organization header.
`createContentClient({ apiUrl, store }).page('home')` returns the published page.
Render its `content.sections` with the storefront's own components. Handle an
unpublished/missing page separately from network or server errors.

Prefer one `store-page` record per page, with embedded sections. Five sections do
not need five templates or records. Load the page once on the server and pass its
sections down. Catalog references need their own bounded catalog reads: reuse
repeated references and run independent reads in parallel. Do not refetch CMS data
after hydration when the server has already supplied it.

The SDK supplies Next revalidation options (60 seconds by default), not a universal
cache or single-flight implementation. Use the host framework's shared server
loader when several components need the page. Explicit `cache: 'no-store'` opts out.
Cache identity must include the store. For manual invalidation, follow the signed
refresh contract in the guide; publishing alone does not send a webhook.

Entry database IDs are generated by the server. Page keys such as `home` are
caller-supplied and permanent in this API. They are unique per store, template and
language: two stores may both use `home`. Never add organization prefixes to solve
an apparent collision. Section IDs are page-local: generate new IDs for new or
duplicated sections and preserve them on edits/reordering; the portal does this.

For merchant editing, use `createMerchantContentClient` with store-scoped bearer
credentials on trusted surfaces. Open a complete listed entry directly. Preserve
its captured `__v` for writes and publication actions; retain the user's draft on
conflict. Integration API keys do not grant CMS management access in this contract.
Save draft and publish are separate operations. Keep staff credentials out of
public bundles.

For merchant TanStack caching, use `createContentQueries(cms, session.id)` from
`@classytic/commerce-client/query-options`. Use its keys consistently for reads
and invalidation; the session ID is a non-secret cache scope, never a bearer token.
